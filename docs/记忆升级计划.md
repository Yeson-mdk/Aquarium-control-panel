> 目标：把「记了但不会想」补成 Generative Agents 的完整闭环。四个阶段按依赖排序，**每阶段独立可上线、独立可回滚**，做完一个传一次 NAS，跑稳了再开下一个。

# 阶段一：群聊日结 + 重要度打分（1-2 晚）

## 目标
群聊和好友私聊进记忆流；重要度由模型标（1-5），不再写死。**一个改动补两个缺口：重要度不单独做逐条打分模块，融进日结输出。**

## 任务清单
- [ ] 1.1 `panel/qq/owner.mjs` 新增 `digestGroup(peer, since, remember)`（照 `digestToday` 抄骨架）：
  - 输入：`readChat(peer)` 里 **`since`（上次日结时间戳）之后** 的记录（`kind !== 'reset'` 过滤）。**按「上次日结到现在」切窗口，不按自然日**——第一次跑 since 取启用当天零点，不回溯历史；顺带修掉跨午夜热聊被劈成两个碎 digest 的问题
  - 前置水楼过滤：先去掉完全同文的消息和纯表情/图片标记，**过滤后**不足 6 条直接 return null（冷清群、刷屏水楼都不结）

  - **src 溯源锚点（防「事实压缩幻觉」）**：每条 item 必须带原话片段，人工排查时顺着 src 回 jsonl 对账，分得清「合理概括」和「编造」；src 缺失的条目照写、锚点留空，不因此丢弃

  - text 前缀写清来源：群聊 `「群·群名」人名：概括`，好友私聊 `「私·名字」：概括`——recall 时一眼知道哪来的

# 阶段二：反思产出洞察写回流（1-2 晚 + 观察一两周）

## 目标
补 GA 最核心的闭环：反思不只在改自画像，还产出**带出处的洞察**，作为一等公民记忆写回流里——可被 recall、可参与下一轮反思。顺带补阶段一漏掉的一半：群/好友的 chat 记忆按对话放行（2.8）。

## 任务清单
- [ ] 2.1 `panel/mind.mjs` `reflect()` 里加一次 LLM 调用（在写「最近的我」之后）：
  - ⚠️ **输入不是现成的**：`reflect()` 现在只读当天 B站 独白，记忆流要**新接一路输入进去**（照 `maybeEvolvePersona` 里 `memoryView(60)` 的用法抄，那是过滤列表真正所在）。工程量按「新接一路」估，别按「现成的」估
  - 输入：当天记忆流尾部 25 条（阶段一产出的群聊条目自动就在里面）——**每条前面带它的 `id`** + 昨夜已有的洞察（去重、可推翻用）
  - ⚠️ **洞察会间接漏进性格演化**：洞察写回流是 `kind:'self'`、不带 `g:/p:` 钥匙，`maybeEvolvePersona` 的钥匙过滤挡不住它——从群聊长出来的洞察（关于朋友的结论）会进人设输入。人设提示词里「只写她自己长出来的变化」还约束着，不是硬伤；实施时在洞察提示词补一条「可以洞察朋友的事，但那是关于他们的结论，不是她自己的变化」，观察期顺带盯 `personaHistory` 有没有长歪
  - 输出 JSON：
    ```json
    { "insights": [ {"text": "一句结论，第三人称", "from": ["依据记忆的id"], "why": "一句人话依据，给人看"} ] }
    ```
  - **from 用机器可读的记忆 id**（条目自带 id，`memory.mjs:83`）：写不进 id 的依据不可信，非法 id 直接忽略该条；`why` 只是给人看
  - **产出 0-2 条都合法（上限从 5 压到 2）**：归纳推理是幻觉第二大源头，几条碰巧相似的记忆会被强行捏出因果——**宁可少，不要错**；没什么可洞察就空数组，别硬凑
  - 同一次调用里自判矛盾（不建独立检测器）：**和输入记忆明显矛盾的洞察不许写；洞察只能归纳已给出的记忆，不许创造输入里没有的对话、场景、事件**——便宜模型对这种「只许用给到的素材」的事实约束，服从度远高于「不要猜测」类软话
- [ ] 2.2 洞察写回流：`memory.add({ kind:'self', imp: 5, text: '洞察（依据：why）', src: from对应的原句 })`
  - `kind:'self'` 已存在且强度 99 永不遗忘（`memory.mjs:68`），不用新机制
  - 与已有洞察语义重复的（模型判断）不重复写
  - **self 条目软上限 150**（正确但陈旧的洞察只进不出，一年会攒几百条）：活的（非 dead）self 超过 150 时，提示词里加一句「把新洞察往最相近的旧洞察上合并改写：retire 旧的、写一条新的」——一行提示词，不建机制
- [ ] 2.3 **洞察可被推翻（防错误洞察永久驻留）**：reflect 输出可多一个 `"retire": ["要推翻的旧洞察id"]`；
  - `memory.mjs` 加 `retire(id)`：置 `dead: true`，`recall()` 和 `memoryView()` 过滤 dead 条目（**标记失效，不删**——错了还能翻回来）
  - ⚠️ **memdb 侧必须同步，否则 retire 白做**（已核实：`memdb.mjs` 建表没有 dead 列、`rowOf`/`entryOf` 固定八列、`search()` 什么都不滤——recall 想不够数时会从 `memdb.search` 兜底翻旧事，`memory.mjs:152`，不过滤的话被推翻的洞察照样冒出来）：
    - 建表语句加 `dead INTEGER` 列；老库用 `ALTER TABLE mem ADD COLUMN dead INTEGER` 迁移（try/catch 包住，列已存在就跳过）
    - `rowOf`/`entryOf` 带上 dead；`search()` 结果里滤掉 dead（只滤 mem 主表，fact 留底表不动）
  - 输入里已带昨夜洞察及其 id，模型看到新记忆和旧洞察矛盾时自己提 retire
- [ ] 2.4 **召回降权 + 可选审核池（防幻觉正反馈闭环）**：洞察一旦入库是高权重记忆，聊天、下轮反思、晨间计划全都会复用——一条假洞察会污染后续所有行为，所以：
  - `recall()` 打分处给 `kind:'self'` 乘个折扣（如 0.7，进 tuning 可调）：猜想类记忆不该和亲历的事同权重出场
  - **可选开关 `mind.insightReview`（默认关）**：开了之后洞察先不回流，进「待审池」（照 bilibili review 范式，logAction 提醒号主，号主在面板放行才转正）。上线头两周幻觉还凶就开着，稳了再关——代价是号主要人工点一下，别长期开
- [ ] 2.5 自动可用，不用接线：
  - recall：走 memdb search，新条目 syncAll 后自动可翻 ✓
  - 下轮反思：记忆流尾部自动包含 ✓
  - 聊天上下文：personaPatchText / 记忆注入路径看要不要带最近 3 条洞察（先不带，观察 recall 够不够）
- [ ] 2.6 面板「记忆」页加「洞察」一栏：`memory.mjs` 的 view 函数（`:173`）加 `insights: all.filter(e => e.kind === 'self' && !e.dead).slice(-n).reverse()`；`panel.mjs` API 带出来；`app.js` 记忆页渲染一栏，带日期；被 retire 的灰显或折叠，别真藏死；开了审核池的话待审洞察单独一块，带放行/丢弃按钮
- [ ] 2.7 logAction：`💭 今晚的洞察：N 条${retire数 ? `，推翻 ${retire数} 条旧的` : ''}`（都空就不记）
- [ ] 2.8 **补阶段一：群/好友的 chat 记忆按对话放行**（独立于洞察，和阶段二一起上；阶段三晨间计划是全局视角不走这条，阶段四向量检索和 LLM 精排必须复用同一条——精排拿到的候选必须是 scope 过滤之后的名单）
  - 现状：`brain.contextText` 对非号主只 recall `kinds:['watch','social']`，`kind:'chat'` 全被挡掉；群聊/好友日结虽然写进了记忆流（keys `g:群号` / `p:QQ号`），但**她本人在群里/好友私聊里用不上**，只有号主、面板、CLI 能翻。阶段一的召回闭环缺这一半。
  - 口径：可见性按对话白名单，不按“是不是 chat”一刀切——
    - `watch/social`：照旧全局可 recall（谁都能想起她刷过的 B站生活，不含别人的私聊/群聊）；
    - `chat`：只允许 `keys` 里**包含当前对话钥匙**的条目：群聊只认 `g:当前群号`，好友私聊只认 `p:当前QQ`；
    - `owner`、别的 `g:`、别的 `p:`：一律不返回。宁可少想起来，也不能串场。
  - 实现：`memory.recall()` 加一个 `scopeKeys`（或 `peer`）选项，过滤 `kind:'chat'` 的条目；`memdb.search()` 的归档兜底要带同一个 scope（否则被 tidy 归档的旧条目会从档案里漏出来）；`brain.contextText` 把当前 `peer` 传进去。`brain` 的 `recall` 工具是号主专用，不加 scope。只加过滤，不新增模型调用。
  - 测试：
    - A 群能 recall A 群自己的 chat 记忆；
    - A 群 recall 不到 B 群的、也 recall 不到号主私聊的；
    - 好友私聊只 recall 自己 `p:` 的，不碰别的 `p:`/`owner`；
    - 同一个查询走 `memdb.search` 归档兜底时，可见性跟主路一致；
    - 号主上下文不受影响；非号主的 `watch/social` 仍全局可见。
  - 验收：在 A 群问“上次我们聊的那个游戏”，她能翻到 A 群日结；去 B 群问同样的话，翻不到 A 群的条目。
  - 回滚：`scopeKeys` 不传就退回现在的行为（非号主只看 watch/social），不需要删数据。

# 阶段三：晨间计划（2-4 天，单独一轮测试，碰真实账号要慎重）

> **分段（2026-11-12）**：A段 = 时辰表 + 类型/goal + 护栏 + 重排，已上线待验收（见下）；B段 = 内心行为扩充 + 计划元复盘，见 A段之后。顺序：A段观察三天 → B段 → 阶段三.5（约定）。

## 目标
todayPlan 从静态时辰表变成每天早上生成、被打断能重排。失败时**行为不劣于现状**。

## 任务清单
- [x] 3.1 `panel/autopilot.mjs` 新增 `morningPlan()`：
  - 触发：每天第一次 tick 进「第一个时辰」之前；当天已生成过就跳过（`plannedOn` 日期戳，照抄 `reflectedOn` 范式）

  - 每格可带可选 `goal` 短文本（「这次浏览/评论想干什么」，比如顺着某条洞察去看看）——有 goal 才算意图，没 goal 就只是动态时辰表

    1. 白名单外的类型 → 该格回退静态表
    2. 今日上限（todayCounts / config 上限）已满的类型 → 换成 rest
    3. 解析失败/超时/接口挂 → **整表回退静态时辰表**，记 logAction「计划生成失败，用默认表」
  - **执行反馈**：带 goal 的格子执行完，写一条普通记忆（`kind:'watch'/'social'` 照任务类型，imp 2-3）：做了什么、结果如何（成功/没找到/放弃）——这是计划的闭环，不然计划只是轮换表。晨间计划是全局视角，**不套 2.8 的 peer scope**；反馈记忆也不要带 `g:/p:` 钥匙，免得以后被当成某个对话的记忆。

  - **可测性：计划相关的时间统一走一个 `now()` 入口**（`morningPlan` / tick 都接受 `now` 参数）——「集成测试跑一天模拟」这条用例要能写，前提就是时钟能注入；现有代码里裸 `Date.now()` 散落多少改多少，只改计划路径上的
- [x] 3.2 重排触发（三处，都调 `morningPlan({ replan: true })` 只重排剩余时辰）：
  - pause off 之后（号主说「好了」，当天计划可能过时）
  - 号主派活打断之后（addTask executor='bot' 时）
  - 时辰错过之后（autopilot 已有「错过」标记，`autopilot.mjs:10` 注释提到）
  - **重排闸：一天最多 2 次**（`replanCount` 按天计）——「错过→重排→又错过」在 autopilot 抽风时会一晚打转，每次还烧一次模型调用，到次数就锁死剩余时辰照静态表跑
- [x] 3.3 面板「自动养号」页展示：今天她给自己排了什么、哪格是重排的
- [x] 3.4 计划持久化：~~`data/plan-YYYY-MM-DD.json`~~ **改用 `state.plans` 单一来源**（时辰表本来就在里面，类型/goal/replanned 直接挂在格子上，`plannedOn`/`replanCount` 也在 state——不开第二个真相源）

# 阶段三.5：约定（守约式主动开口，2026-11-12 立项；2026-11-17 完成）

> 起因：卷心菜在群里约她「第二天早上 9 点找他」，她因为纯被动回话没去。晨间计划的 `social_init` 白名单口子继续**保留不用**——那种「泛主动」解决不了带截止时间的承诺。这轮做的是「守约」：开口理由是别人先约的，社交上是赴约不是搭讪，人设风险低得多。

## 目标
群里/私聊里「指向她 + 含时间或事件」的约定被识别、存下、到点她在**同一个会话**里主动说一句（自己写、过仲裁人设检查）。没识别出来 = 行为和现在完全一样。

## 任务清单（全是现有零件的拼装）
- [x] 识别：聊天落库后加一步抽取（照洞察那套：LLM 抽 + 只认「指向她」的句子 + 带 依据消息id）。指向判定**复用打分闸 direct 那套**（叫名字/回她的话），不新发明
- [x] 存储：`tasks.json` 加 `dueAt` 字段，约定 = `executor:'bot'` 的一种任务，不开新文件
- [x] 到点：autopilot tick 扫到期约定（30 秒一拍现成的）；**过期超过 1 小时不再发**（怎么处理见待决点①）
- [x] 发送：到点让她自己写一句（上下文 = 当时对方原话 + 跟这个人的近期记忆，friends 防串场），发回原 peer。**实现口径**：人设检查走 llm.chat 带 PERSONA 系统提示，不走 reviewJoin 仲裁——赴约是「到点主动开口」没有触发文本可回，语义不同（实现方案 §4 的 ⚠️）
- [x] 护栏：赴约次数不设上限（2026-11-17 号主改，原「每天最多 2 条」作废）；过期超 1 小时不发；全部兑现落日志，面板可见；识别抽取是 LLM 调用，挂睡前低峰跑；约定不算「新派活」，不触发时辰重排

## 待决点（动手前号主选）
1. **过期了怎么办**：a) 放弃 + 写进她自己的日记式记忆（「忘了赴约」也是人设） b) 晚到也补一句「抱歉刚看到」
2. **识别的指向判定用哪档**：只认叫她名字/回她的话（准但漏），还是加「明显在对她说的语境」（全但可能误识别）——倾向先紧后松

## 测试用例
- [x] 「指向她 + 明天9点找我」的群聊落成一条带 dueAt 的约定；不指向她的同款句子不落
- [x] 到点：只发原 peer、内容过仲裁、同一拍多条全兑现且不重复、不再触发时辰重排
- [x] 过期超 1 小时不发；识别接口挂了不炸、不落垃圾约定

# 阶段四：两段式语义检索——向量粗排 + LLM 精排（可选；前三阶段跑顺后再评估要不要做）

> 2026-11-10 按外部提案（embedding 粗召回 top20-30 → LLM 批量打相关性分 → S = wr·recency + wi·imp + wrel·rel）评估后定稿：方向可行（标准 RAG 两段式），但贴现有架构要改四点，见下。

## 评估结论：方案可行，四处必须改造
1. **打分公式不用新建**：`memory.mjs:155` 已经就是 S = W.recency·recency + W.importance·(imp/5) + W.relevance·rel（W={1,1,2}）。方案里的「新公式」唯一的增量是把 rel 这一项的来源从关键词升级——阶段四动的是 rel 怎么算，公式和权重结构不动。
2. **精排绝不能每条消息都跑**：recall 在每条回复的热路径上（`brain.mjs:528` contextText，回复前同步跑），聊天模型已是 v4pro、本来就慢，精排再串一个 LLM 调用等于每句话多等 2-5 秒。精排必须「触发了才跑」+ 结果缓存，目标触发率 < 20% 的回复。
3. **recall() 的同步签名不能动**：它被 CLI、测试、recall-check、mind、social 全线同步调用，改 async 会全炸。做法：recall() 保持同步（它就是粗排），精排做成独立的 async 步骤（`memory.mjs` 新 export），只有聊天路径（contextText）选择性调用；其余调用方一律不碰。
4. **可见性在粗排就定死**：2.8 的 scope / dead / kinds 过滤都发生在候选集合生成时——精排拿到的候选已经放行过，它只许改排序、不许改可见性、也不许把 MIN_REL 滤掉的条目捞回来（捞回=精排越权当了召回用；「换说法翻不到」是 4A 向量该解决的事）。

## 目标
relevance 从「关键词+二字片段」两步升级：先 4A 向量混合（粗排，确定性、零延迟），4B LLM 精排（可选、默认关）只补「粗排拿不准」的场景。**决策点：阶段一二跑顺后若 recall-check 显示「该想起的都能想起」，这阶段永远不做；先上 4A，4B 只在 4A 之后仍有「排序烂/拿不准」的证据时才上。**
⚠️ 向量把「语义相近」和「是同一件事」混为一谈的几率比关键词高——上线后要额外警惕**跨记忆拼接幻觉**（把两件只是像的事揉成一件）。上线头两周多翻 recall-check 的结果，发现拼接就把 kwW 调高。精排同理：它打的是「相关度」不是「同一件事度」，提示词里要按「是不是同一件事/直接相关」出题，不然只像不像的两条会得高分。

## 4A 向量粗排（确定性，零额外延迟）
- [ ] 4.1 embedding 客户端：复用 ModelScope 那套（vision 已走 MS，`llm.mjs` 里有现成 fetch 骨架），独立小函数 `embed(texts[])`
- [ ] 4.2 `panel/memdb.mjs` 迁移：
  - `ALTER TABLE mem ADD COLUMN vec TEXT`（建表语句同步加列，`memdb.mjs:31`）
  - ⚠️ **和 2.3 的 dead 列是同一个坑，只提醒了建表没提醒代码**：`rowOf`/`entryOf`/`ins`（prepare 的 INSERT）也是固定列数的，加列必须三处一起改，漏一处 vec 静默不存
  - 存量回填：一次性脚本 `node panel/backfill-vec.mjs`，1500 条分批（每批 ≤ 20），**支持断点续传**——跳过 vec 已有值的行，接口中途挂了重跑一遍接着来，不用从头
- [ ] 4.3 写入路径：`memory.add` → syncAll 时顺带打向量；**打向量失败 → vec 存 null，检索走老路**（这是上线分界线：API 挂了不影响任何现有行为）
  - ⚠️ `syncAll` 是**同步函数**（node:sqlite 全同步），打向量是网络调用——向量要在 `add()` 里异步打完再落库，别塞进 save/syncAll 里，会把所有同步路径拖进网络等待
- [ ] 4.4 检索路径：`memdb.search()` 里 relevance = 关键词分 × kwW + 向量余弦 × vecW；**两个系数进 tuning**（默认 0.4 / 0.6，面板可调）——余弦和关键词分值域不一定对齐，固定配比很容易一方碾压另一方，必须留调的口子；查询侧没配 embedding 模型 / vec 全空 → 纯关键词（现状）。**先按 2.8 的对话 scope 过滤，再算分/排序**：向量只影响排序，不影响可见性。
- [ ] 4.5 面板「手感调参」或 QQ 设置加一个 embedding 模型名输入框（留空=不用）
- [ ] 4.6 上线前对照：用固定查询集（见通用纪律）跑「纯关键词 / 纯向量 / 混合」三路，人工比一遍再定系数

## 4B LLM 精排（默认关；只在 4A 之后仍有排序问题才上）
- [ ] 4B.1 开关与触发（三条同时满足才跑，缺一就静默走粗排结果）：
  - config 精排模型非空（新字段 `memory.rerankModel`，默认空=关；用 flash 这档就行——它是打分不是写作）
  - 粗排结果「拿不准」：top1 与 top3 分差 < 阈值、或入围条目的 rel 全低于另一条线（两个阈值进 tuning，起步 0.5 / 0.35 观察）——一眼断层领先的翻查不值得多花一次调用
  - 缓存未命中（命中直接用旧分）
- [ ] 4B.2 精排调用（`memory.mjs` 新 export `async rerank(query, candidates)`，只被 contextText 调）：
  - 输入：粗排 top 20-30 候选（**已过 scope/kinds/dead/MIN_REL**，精排见到的就是放行后的名单），每条带 id + text，加查询原文
  - 提示词只给事实和输出格式、不给例句（通用纪律 4）：任务=判断每条和查询说的是不是同一件事或直接相关；输出 JSON、按 id 键、值 0~1；只许用给到的 id，不认识的 id 忽略；没有相关的全 0 也合法；除 JSON 外不许输出任何字
  - **必须按 id 键、绝不按序号**——小模型按位置对齐会错位，错一位整批白打
  - temperature 0；**maxTokens ≥ 200**（flash 前置消耗大，小上限回空串，见 deepseek-flash 教训）
  - 解析失败 / 超时 / 空输出 → 静默退回粗排排序，不重试不报错（精排是锦上添花，不是依赖链）
- [ ] 4B.3 分数融合：rel_final = rW·rel_llm + (1-rW)·rel_coarse，rW 进 tuning（默认 0.7）——单次 LLM 打分有噪声，整体替换不如混合稳；S 公式不变（`memory.mjs:155`），contextText 拿 rel_final 重排后再取 top-k
- [ ] 4B.4 缓存：key = 规范化 query + 候选 id 集合，落 `data/rerank-cache.json`（LRU 几百条）；同 query 短时间内不重复调模型
- [ ] 4B.5 touch 照旧只落在最终 top-k 上，精排环节不 touch
- [ ] 4B.6 **recall-check 夜间回归继续走纯粗排**（不触发精排）：精排一开排名就带上模型当天的随机性，回归报警会变得没法归因——回归基线必须停在确定性路径上

## 测试用例
- [ ] vec 为 null 的条目照常参与关键词检索
- [ ] embed 接口挂 → 写入不炸、检索自动退关键词
- [ ] kwW / vecW 能被 tuning.json 覆盖（照 topic/gate 的 merge 范式）
- [ ] 有向量时混合分排序 vs 纯关键词排序，抽查 10 个查询更合理
- [ ] 向量检索同样过 2.8 的对话 scope：A 群的查询不能因为向量相似把 B 群/号主记忆返回
- [ ] 精排关着（默认）：行为与 4A 完全一致，一次模型调用都不多
- [ ] 精排输出里出现候选没有的 id → 忽略该条不炸；输出非 JSON → 退粗排
- [ ] 精排调用失败/超时 → 排序与粗排一致
- [ ] 缓存命中不再调模型（调用计数不涨）
- [ ] A 群查询的精排候选里不出现 B 群/号主条目（可见性在粗排定死）
- [ ] 粗排 MIN_REL 之下被滤掉的条目，精排不能把它捞回 top-k（防精排越权当召回）

## 验收
- 4A：挑 10 个以前 recall 翻不到的「换了个说法」的查询（比如她记得「烧腊饭」，问「吃的」），≥7 个能翻到。
- 4B：开精排跑固定查询集，「粗排排序 vs 精排排序」人工比 10 个，≥6 个更合理；且精排触发率 < 20% 的回复（超出=触发条件定错，先调阈值再谈效果）。

## 回滚 / 传 NAS
- 回滚：清空 rerankModel 即回 4A；再清空 embedding 模型即回关键词法（现状）；vec 列和 rerank 缓存留着无害
- 传：`panel/memdb.mjs`、`panel/memory.mjs`、`panel/llm.mjs`、`panel/panel.mjs`、`panel/public/app.js`、`panel/qq/brain.mjs`（contextText 接精排）+ 新增 `panel/backfill-vec.mjs`
