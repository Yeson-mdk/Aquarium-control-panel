# 定时任务扩展——审视与工程量（待号主裁决，暂不改代码）

> 2026-11-18。起因：号主觉得阶段三.5 的「赴约」太片面，希望升级成**通用定时任务**：视频观看、每日提醒、赴谁认谁、跨会话执行。
> 这份只做三件事：① 对照原三.5 现状 ② 拆新需求、逐条定位差距 ③ 评估工程量与分期。**代码一行没动。** 裁决后再按分期实施。

---

## 0. 一句话结论

原三.5 做的是「**到点在同一会话发一句话**」，核心假设是 *动作=说一句*、*目标=来源会话*、*时间=一次性*。
你的新需求正好把这三条假设全打破了（动作要能看视频、目标要能跨会话、时间要能每天重复）。
所以这不是「给赴约打补丁」，而是**把 appointment 泛化成 job（定时任务）**，赴约退化成 job 的一种动作（`kind:'say'`）。
工作量约为原三.5（2.5 晚）的 **2 倍**，其中跨会话是大头，建议分三期。

## 1. 原阶段三.5 现状基线（已实现，逐条对照）

设计稿见 [`阶段三.5约定实现方案.md`](./阶段三.5约定实现方案.md)，实现见 `panel/qq/appoint.mjs`。

| 环节 | 现状 | 关键位置 |
|---|---|---|
| 数据 | 约定 = tasks.jsonl 一条 `type:'appointment'`，带 `dueAt / peer / originText / originMsgId / who` | `appoint.mjs:29 addAppointment` |
| 识别A（号主） | `set_appointment` 工具（号主专用），模型在 reply 里调，LLM 给 dueAt、程序校验未来且 ≤7 天 | `tools.mjs` / `brain.mjs` |
| 识别B（他人） | 夜间链扫当天活跃对话，`direct` 正则认指向她的句子，LLM 抽约定 | `appoint.mjs:115 scanForAppointments` |
| 触发 | autopilot tick 每 30s 扫到期，不受养号总开关影响，过期 >1h 不发，不设上限 | `appoint.mjs:45 scanDueAppointments` |
| 发送 | 号主→`notify.rawSend` 直发；他人→`sendText(text,'appointment',peer)` 发回**来源会话** | `appoint.mjs:65 fulfillAppointment` |
| 面板 | `/api/appointments` 列表 + 取消 | `panel.mjs` |

**三条硬假设**（新需求全部要改）：
1. 到期动作写死 = 生成一句话（`draftOwnerLine` / `draftHonorLine`）；
2. 回复目标 = 来源 `peer`，没有「另一个会话」概念；
3. `dueAt` 单次，`status='fired'` 即终结，没有重复。

## 2. 新需求拆解与差距定位

按你说的括号规则理解开放范围：**无括号=所有人开放，括号内=限定范围**。

### 需求① 视频链接观看任务（限号主）
> 私聊/群聊发 B站链接叫她看（几分钟后或现在），到点看完再回复。**仅对用户（号主）生效。**

- **现成零件**：`runTask` 已支持"点名看某个视频"（`autopilot.mjs:1001`，`runSession` 的 `directive`，628 行 `noSkip: !!videos?.length` 即"你点名的视频不划走"）；`bili_task` 工具已能交后台（`tools.mjs:103`）。
- **缺什么**：
  1. `bili_task` 是**立即执行**，没有"延迟到 dueAt 再跑"——定时任务框架缺动作分发；
  2. 到期动作只会"发一句话"，不会"跑一个任务"；
  3. 链接/BV 号解析与落库（`payload.bvid`）现成度低，要新写；
  4. 权限闸：非号主的视频请求要拦（只号主可建）。
- **即时性**：「几分钟后」等不到夜间扫，必须走**号主工具即时建任务**（在 reply 里调），不能靠 `scanForAppointments`。

### 需求② 每日重复（所有人开放）
> "每天几点叫他"，每天到点执行。

- **缺什么**：`dueAt` 单次模型不够。要加 `repeat:'daily'`，触发后**不 fired 而是推进到下一次**（`nextDueAt`），面板要显示"每天 HH:mm"，还要有到期上限（否则无限累积）。
- 识别层 prompt 要能区分"明天8点"（once）和"每天8点"（daily）。

### 需求③ 赴约认人（所有人开放）
> 赴约时记得赴**谁的**约，不要在群里广泛赴约。

- **现成零件**：`who`、`draftHonorLine` 已带该人近期记忆防串场、`findGroupMember` 能把名字映射成群成员 @（`index.mjs:403`）。
- **缺什么**：群里赴约是**裸发**（`index.mjs:519` 注释明说"群里裸发文字，不带 @"），没有 `[TO:who]`，所以看着像"对着空气说"。这是"广泛赴约"观感的**真正根因**——修起来最便宜。
- 改法：赴约群消息强制带 `[TO:约你的人]` → `sendText` 自动转 @；prompt 加"只对约你的人说一句，不是群公告"。

### 需求④ 跨会话执行（权限分级）
> 私聊里说"在哪个群发/做何事"，群聊里说"去私聊做何事"。**除号主外：只能群↔私，不能群↔群；号主全开。**

- **现成零件**：`sendText(text, kind, peer)` 已能发往任意 `owner / g:群号 / p:QQ号`（`index.mjs:508`），`peerTarget` 解析现成——**发送层不用改**。
- **缺什么（这是大头）**：
  1. 数据层要把"来源"和"目标"拆开：`sourcePeer`（谁在哪下的令，判权限用） vs `targetPeer`（去哪执行/回复）；
  2. **群名→群号映射没有现成的**。`findGroupMember` 是"人名→群成员"，不是"群名→g:群号"。要新建群目录（收消息时顺手记 `g:群号 → 群名`），或让号主手动登记，否则"去那个测试群发"解析不了；
  3. 识别层要抽"目标会话意图"（哪群/私谁），并做权限矩阵校验；
  4. 同名群歧义要处理（宁可问一句，别发错群）。

**权限矩阵**（建议照此实现）：

| 发起人 | 来源 | 允许目标 | 禁止 |
|---|---|---|---|
| 号主 | 任意 | 任意（含群→群） | 无 |
| 好友 | `p:` 私聊 | 自己私聊 ↔ 群 | 冒用他人身份 |
| 群友 | `g:` 群 | 该群 ↔ 自己私聊 | 群→**别的群** |

## 3. 数据结构建议（核心改动）

把 `type:'appointment'` 泛化成通用 job（**保留旧字段兼容读取**，老约定不迁移也能跑）：

```jsonc
{
  "id": "...", "type": "job",            // 旧数据是 'appointment'，读取时两种都认
  "kind": "say | watch | task",           // 新增：说一句 / 看视频 / 交后台任务
  "at": 1731798000000,                    // 即原 dueAt（兼容读 dueAt）
  "repeat": "once | daily",               // 新增：每天重复
  "sourcePeer": "g:9003",                 // 新增：谁在哪下的令（判权限）
  "targetPeer": "p:10086",                // 新增：去哪执行/回复（跨会话）
  "who": "卷心菜", "whoQq": "10086",       // 原 who + 新增 @ 用的 QQ
  "originText": "明天9点找我", "originMsgId": "msg_x",
  "payload": { "bvid": "BV1xx", "taskNote": "" }, // watch/task 的参数
  "status": "pending | fired | done | failed | expired | cancelled",
  "nextAt": 1731884400000                 // daily 推进到下一次
}
```

触发层从"逐条发一句话"改成"按 `kind` 分发"：
- `say` → 现有 draft + sendText（赴约+@）；
- `watch` → `runSession({ directive: 看该 bvid })`；
- `task` → `runTask(addTask(...))`。

## 5. 风险提示

1. **视频任务吃真实风控预算**：`watch` 会真的打 B站 接口，公域触发必须严控。建议视频任务**只给号主**（你的括号也这么写的），且加每日上限。
2. **跨群群名歧义**：同名群发错群比不发更糟。群目录要有"不确定就问一句"的兜底。
3. **daily 无限累积**：每天一次的约定会越攒越多，要有过期（如 30 天没触发自动取消）和总量上限。
4. **即时识别的成本**：视频任务"几分钟后"不能等夜间扫，但**别在每条消息上都调 LLM**——走号主工具即时建任务，群友/好友仍走夜间批量扫。
5. **老数据兼容**：一期改数据模型时保留 `appointment`/`dueAt` 的读取兼容，避免历史约定变孤儿。

## 6. 号主裁决（2026-11-18 已定，按此实施）

1. **"用户" = 号主**：视频观看任务只对号主开放，其他人发了也不建任务。
2. **任务保留 30 天**；建每日任务时**在她回复里口头告知发起人**（"每天 X 点叫你，连着 30 天"这种），**不要客服腔、不要"已为您设置"**。
3. **群名解析：面板新增一张"群号↔群名"表**，群号自动带出、群名由号主自己填（初期方案，后期再想更省的）。跨群执行时查这张表把群名翻成 `g:群号`。
4. **旧 `appointment` 数据兼容读取**，不迁移。
5. **群赴约强制 @ 没问题**；但**每日任务要加中止入口**——被赴约人在 30 天中途说"不用继续了"，识别后把该 daily 任务标 `cancelled` 停掉。
